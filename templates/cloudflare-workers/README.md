# Cloudflare Workers Overlay — Adoption Guide

Part of `christopher-coding-standards`. Applies to TypeScript projects deployed on
**Cloudflare Workers** (Wrangler, D1, KV, Queues, Cron Triggers).

**This overlay layers on the [TypeScript overlay](../typescript/README.md).** Adopt the
TS overlay first, then apply this one. This overlay does **not** redefine Biome,
pre-commit, or Gitleaks — those come from the TS overlay unchanged. It changes only
what Workers require: the tsconfig, the test runner, and the build/deploy toolchain.

---

## What this overlay adds (and what it reuses)

| Concern | Source | Notes |
|---|---|---|
| Formatter + linter (Biome) | **TS overlay, unchanged** | `noExplicitAny`, `noNonNullAssertion` still apply |
| Pre-commit + Gitleaks | **TS overlay, unchanged** | secret scanning still applies |
| `tsconfig.json` | **this overlay (replaces base)** | adds workerd types + `worker-configuration.d.ts`, `noEmit` |
| Test runner | **this overlay (replaces base)** | runs inside workerd via `@cloudflare/vitest-pool-workers` |
| Build / dev / deploy | **this overlay** | `wrangler` |
| Typed bindings (`Env`) | **this overlay** | generated by `wrangler types` |
| Mutation testing (Stryker) | **TS overlay, on logic modules only** | see "Mutation testing" below |

---

## Why Workers needs its own overlay — the security angle

This overlay is not just plumbing. Two Workers facts map directly onto the standard's
"forbid, don't warn / contain by capability" philosophy:

- **Bindings are capability grants.** A Worker can only reach a resource (a D1 DB, a KV
  namespace, a queue) that is declared in `wrangler.jsonc`. Least privilege is therefore
  enforced by *configuration*, reviewable in a diff — not by runtime discipline. Treat
  every new binding as a security decision.
- **Secrets must never live in `vars`.** `vars` is plaintext, committed config. Secrets go
  through `wrangler secret put` or a Secrets Store binding. Gitleaks (from the TS overlay)
  catches secrets in *source*, but will not reliably catch a low-entropy token pasted into
  `vars` — so this is a hard **review rule**, called out in the `wrangler.jsonc` template.

## Adoption steps

### 1. Adopt the base TypeScript overlay first

Follow [`../typescript/README.md`](../typescript/README.md). Then come back here.

### 2. Copy the Workers files into your repo root

```
wrangler.jsonc        → repo root  (replaces nothing; this is new)
tsconfig.json         → repo root  (USE THIS INSTEAD OF the TS overlay's tsconfig.json)
vitest.config.ts      → repo root  (USE THIS INSTEAD OF the TS overlay's vitest.config.ts)
```

Keep the TS overlay's `biome.json`, `.pre-commit-config.yaml`, and `Makefile`.

### 3. Merge the package.json snippet

Open `package.json.snippet` and merge its `scripts` and `devDependencies` into your
`package.json` (already containing the base overlay snippet). The Workers snippet
**bumps Vitest to 4.1+** — required by the Workers pool. Bump `vitest` and
`@vitest/coverage-v8` together.

```bash
npm install
```

> Toolchain is **npm + wrangler** (per the social-media-automation OQ-7 decision). The base
> overlay's README mentions pnpm; on a Workers project use npm so it matches `wrangler`'s
> conventions and this snippet's lockfile.

### 4. Fill in `wrangler.jsonc`

Set `name`, pin `compatibility_date` to today, and uncomment **only** the bindings this
Worker actually uses. Every binding you add widens the Worker's reach — add deliberately.

### 5. Generate the typed `Env`

```bash
npm run cf-typegen        # wrangler types → worker-configuration.d.ts
```

Re-run this after **every** change to `wrangler.jsonc`. The `typecheck` script runs it
automatically before `tsc`, so types can't silently drift from config. Commit
`worker-configuration.d.ts`.

## Writing tests (workerd runtime)

Tests run inside the real workerd runtime, so bindings behave as in production.

```typescript
import { env } from "cloudflare:workers";
import { createExecutionContext, waitOnExecutionContext } from "cloudflare:test";
import { describe, it, expect } from "vitest";
import worker from "../src/index.ts";

describe("fetch handler", () => {
  it("validates input at the boundary", async () => {
    const ctx = createExecutionContext();
    const res = await worker.fetch(new Request("https://example.com/"), env, ctx);
    await waitOnExecutionContext(ctx);
    expect(res.status).toBe(400); // rejects unvalidated input
  });
});
```

`cloudflare:workers` exports `env` (your typed bindings). `cloudflare:test` exports the
harness helpers — including ones that match common server-side-gate patterns:

| Helper (from `cloudflare:test`) | Use it to test |
|---|---|
| `createExecutionContext` / `waitOnExecutionContext` | any handler's lifecycle |
| `createScheduledController` | Cron Trigger handlers (`scheduled`) |
| `createMessageBatch` / `getQueueResult` | Queue consumer handlers (the rate-limited gate) |
| `applyD1Migrations` | seed D1 before a test that reads/writes it |

## Mutation testing

Stryker's vitest-runner **cannot** drive the workerd pool. Do not try to mutation-test
inside the Workers runtime. Instead:

- Keep pure business logic (validation, transforms, policy decisions) in modules that don't
  import `cloudflare:*`, and mutation-test those with the **base** overlay's `stryker.config.mjs`.
- Use this overlay's `vitest.config.ts` for integration tests that need real bindings.

This split is also good design: the security-critical decision logic stays runtime-agnostic
and gets the strongest test gate.

## Verification test

After adoption, confirm the gates are live:

1. **Strict types bite** — in a handler, read `env.SOMETHING_NOT_IN_WRANGLER`. `npm run typecheck`
   must fail (the generated `Env` has no such key).
2. **Secret discipline** — confirm no credentials appear under `vars` in `wrangler.jsonc`;
   real secrets are set via `wrangler secret put`.
3. **Workerd tests run** — `npm test` executes inside workerd and `env` bindings resolve.
4. **Inherited gates** — the TS overlay's Biome/Gitleaks pre-commit hooks still fire (see the
   TS overlay's verification test).

If any gate does not fire, stop and diagnose before deploying.
