## Running the maintainer seam

On an authorized suitable Linux-x86_64 CPython3.13 environment, install selected tools into a **new** owned directory:

```sh
python3 tools/ci/install-tools.py typescript --directory /owned/new-ci-tools
```

The installer writes `environment.json` and source/checksum metadata. In GitHub it appends only the selected job's environment/PATH using runner-provided files. Outside GitHub, the caller deliberately applies the recorded environment; never evaluate arbitrary JSON/shell from an untrusted source. Node24.21.0 is selected separately; setup-action execution is not proved by native CLI tests. Then:

```sh
python3 tools/ci/check-reference.py ts-lint --work /owned/new-reference
python3 tools/ci/check-reference.py ts-test --work /owned/another-new-reference
```

Other selected groups/modes: `bash`, `go`, `python`; security groups/modes use `check-security.py`: `gitleaks`, `semgrep`, `trivy`. Work directories must be new; no clobbering of existing trees. Semgrep's resolved `--work` must also remain outside the checkout, including symlink-resolved paths; this is checked before directory creation, scanning or copying private policies. This is maintainers' fixture support, **not** a default consumer payload or a registry/updater/checker-enrollment system. Trusted commands can write undeclared caches/outputs; no sandbox/descendant-supervision claim. Earlier shared-cache observations, including C12's initial pnpm store, are disclosed, not rewritten as pristine isolation. The current installer explicitly selects `npm_config_store_dir`; an actual `pnpm store path` check matched its owned prefix.

The existing narrow C3 checker matches only tool statuses0/1 with unchanged declared workspace inputs and literal diagnostics. TypeScript's actual diagnostic status2 is explicitly assessed by one named command/TS2322 check without changing C3 or normalizing arbitrary errors. The maintainer verifier lives outside consumer source; copying it into Python's `ruff check .` was a retained integration failure, not a consumer rule defect. Missing tools/config/inputs, wrong markers, unavailable checks, unexpected green or arbitrary errors cannot stand in for intended rejection.
